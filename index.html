How I build a payment endpoint

Money-movement code has to survive retries, timeouts and crashes. This sample shows the pattern I use: an idempotency key backed by a unique constraint, and the event written to an outbox table in the same transaction. A retried request returns the original result instead of paying twice, a concurrent duplicate fails on the constraint, and a crash can't lose the event. 

@RestController
@RequestMapping("/api/payments")
class PaymentController {

    private final PaymentService payments;

    PaymentController(PaymentService payments) {
        this.payments = payments;
    }

    @PostMapping
    ResponseEntity<PaymentView> submit(@RequestHeader("Idempotency-Key") String key,
                                       @Valid @RequestBody PaymentRequest request) {
        return switch (payments.submit(key, request)) {
            case Submitted(PaymentView view) -> ResponseEntity.status(HttpStatus.CREATED).body(view);
            case Replayed(PaymentView view)  -> ResponseEntity.ok(view);
        };
    }
}

@Service
class PaymentService {

    private final PaymentRepository repository;   // unique constraint on idempotency_key
    private final OutboxRepository outbox;

    PaymentService(PaymentRepository repository, OutboxRepository outbox) {
        this.repository = repository;
        this.outbox = outbox;
    }

    @Transactional
    SubmitResult submit(String key, PaymentRequest request) {
        return repository.findByIdempotencyKey(key)
                .<SubmitResult>map(existing -> new Replayed(existing.view()))
                .orElseGet(() -> {
                    Payment payment = repository.save(Payment.pending(key, request));
                    outbox.save(OutboxEvent.of("payment.submitted", payment.id()));
                    return new Submitted(payment.view());
                });
    }
}

sealed interface SubmitResult permits Submitted, Replayed {}
record Submitted(PaymentView view) implements SubmitResult {}
record Replayed(PaymentView view) implements SubmitResult {}

Java 21 sealed types and record patterns make the controller's switch exhaustive: add a new outcome and the compiler points to every place that must handle it.
